# Internacionalización — portal Apptonomia

> 🌐 **Other language:** [English](../en/i18n.md)

Este documento es la **referencia de internacionalización** del
portal Apptonomia. Explica cómo funciona la UI español / inglés,
cómo se detecta y aplica el locale activo, y la receta para añadir
un tercer locale.

---

## 1. Locales actuales

El portal se envía con dos locales:

- **Español (`es`)** — predeterminado, fuente de verdad para cada
  clave.
- **Inglés (`en`)** — secundario, paridad espejada desde `es`.

El metaproyecto mantiene intencionalmente el portal bilingüe en
lugar de multilingüe. Cada app hermana de la suite es responsable
de su propia i18n — añadir un tercer locale al portal requiere
tanto actualizar el portal como asegurar que el nuevo locale se
soporta en cada hermano que envíe su propio selector. El locale
predeterminado es `es` porque el público principal de la suite
lee primero en español.

---

## 2. Cómo funciona la detección

### 2.1 En la primera visita

`js/bootstrap.js` se ejecuta **antes** que cualquier otro script
(es la primera etiqueta `<script>` después del pre-paint
inline). Hace:

1. Lee `navigator.languages` (un array de locales preferidos, el
   más preferido primero).
2. Para cada preferencia, pone en minúsculas y quita el sufijo de
   región (`es-MX` → `es`, `en-GB` → `en`).
3. Devuelve la primera coincidencia contra el array `SUPPORTED`.
4. Cae a `'es'` si ninguna preferencia coincide.

### 2.2 En el override manual

El selector de idioma (`🇪🇸 / 🇬🇧` arriba a la derecha del
portal) sobreescribe el locale detectado para el resto de la
sesión. El override **no se persiste en `localStorage`** — el
portal es sin estado a propósito; un refresh vuelve a detectar
desde `navigator.languages`.

### 2.3 En el atributo `<html lang>`

El locale activo se refleja en `<html lang>` para lectores de
pantalla y motores de búsqueda. Esto se establece en el primer
paint (antes de que se carguen las hojas de estilo) por el script
de pre-paint.

## 3. Dónde viven los strings

### 3.1 `js/strings.<locale>.js`

Cada string de UI vive en uno de dos archivos:

- `js/strings.es.js` — español (predeterminado, fuente de verdad).
- `js/strings.en.js` — inglés (paridad espejada).

Cada archivo exporta un único objeto `window.STRINGS` con un
objeto anidado por locale:

```js
// js/strings.es.js (forma canónica)
window.STRINGS = {
  es: {
    'meta.title': 'Apptonomia — suite de actividades',
    'meta.description': '…',
    'cards.calculia.name': 'Calculia',
    'cards.calculia.tagline': '…',
    // …
  }
};
```

`js/script.js` lee desde `window.STRINGS[currentLocale]`. Si
falta una clave en el locale activo, cae al bloque `es` — esto
significa que **añadir una clave a `strings.es.js` siempre es
seguro**; el portal no se rompe antes de que aterrice el espejo
en `en` (simplemente muestra español hasta entonces).

### 3.2 Lo que **no** está en `strings.<locale>.js`

- **Código técnico (HTML, CSS, JS, Markdown, JSON).** Siempre en
  inglés. Variables, nombres de funciones, identificadores,
  comentarios, mensajes de commit — todo en inglés. Esta es la
  política de idioma transversal de la suite (ver `CLAUDE.md`
  §B.2).
- **`lang="es"` en los documentos HTML** (los Markdown / specs
  fuente en `doc/<lang>/` — esos son archivos por idioma, no en
  `strings.<locale>.js`).
- **Nombres de proyecto / repo**: `calculia`, `memofun`,
  `okeymoney`, `routime`, `sinonimia`, `teclatlon` — siempre en
  minúsculas, sin acentos. El nombre a mostrar en cada idioma es
  la forma legible (Calculia, Memofun, etc.).
- **Pictogramas / imágenes**: los pictogramas de ARASAAC mantienen
  su atribución en español (el idioma fuente); cada locale muestra
  la misma atribución.

## 4. Añadir un tercer locale

La receta de abajo añade un nuevo locale — por ejemplo, `gl`
(Gallego).

### 4.1 Checklist

1. **Crea el archivo de strings**: `js/strings.gl.js` con el mismo
   conjunto de claves que `js/strings.es.js`, traducido.
2. **Actualiza la lista `SUPPORTED`** en `js/bootstrap.js`:
   ```js
   const SUPPORTED = ['es', 'en', 'gl'];
   ```
3. **Añade un botón al selector de idioma** en `index.html`:
   ```html
   <button data-lang="gl" aria-label="Galego">🇬🇱</button>
   ```
4. **Actualiza `scripts/check.js`** para incluir `'gl'` en el
   chequeo de paridad:
   ```js
   var SUPPORTED = ['es', 'en', 'gl'];
   ```
5. **Actualiza los badges de `README.md` + `README.es.md`** para
   listar el nuevo locale:
   ```
   [![i18n](https://img.shields.io/badge/i18n-es%20%7C%20en%20%7C%20gl-yellow.svg)](#-documentaci%C3%B3n)
   ```
6. **Traduce los docs**: como mínimo, añade el idioma al
   selector de idioma reflejado en `README.md` / `README.es.md`.
   La traducción completa de `doc/<lang>/` puede llegar después
   (el portal se envía antes que los docs).
7. **Ejecuta `node scripts/check.js`** — debe pasar.

### 4.2 Cosas que verificar

- Cada clave en `js/strings.es.js` tiene una traducción en
  `js/strings.gl.js`.
- Cada clave en `js/strings.gl.js` también existe en
  `js/strings.es.js` (el chequeo de paridad es bidireccional).
- El botón del selector de idioma tiene el emoji / glifo de
  bandera correcto para el nuevo locale.
- El nombre del nuevo locale aparece en `<html lang>` cuando se
  selecciona.
- El `?v=` content-hash en la nueva etiqueta
  `<script src="js/strings.gl.js">` se regenera con
  `scripts/build-head.js`.

---

## 5. Cosas que **no** debes hacer

- **No** envíes un locale donde algunas claves caigan al fallback
  de `es` en producción. La CI (`scripts/check.js`) falla el
  build si alguna clave en cualquier archivo de strings de un
  locale falta en cualquier otro locale.
- **No** uses CSS o estructuras HTML específicas por locale. El
  portal debe renderizarse idénticamente en cada locale; las
  únicas diferencias son los strings.
- **No** introduzcas una convención de nombres de archivo por
  locale distinta de `strings.<locale>.js`. Cada hermano de la
  suite usa el mismo token `<locale>`; la consistencia es lo que
  permite que un futuro paso de build comparta código entre
  hermanos.
- **No** guardes el locale activo en `localStorage`. El portal es
  sin estado a propósito; almacenarlo añadiría una tercera
  fuente de verdad (junto a `navigator.languages` y el selector
  manual) sin una ganancia correspondiente.
