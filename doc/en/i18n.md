# Internationalisation — Apptonomia landing

> 🌐 **Other language:** [Español](../es/i18n.md)

This document is the **internationalisation reference** for the
Apptonomia landing. It explains how the Spanish / English UI
works, how the active locale is detected and applied, and the
recipe to add a third locale.

---

## 1. Current locales

The landing ships with two locales:

- **Spanish (`es`)** — default, source of truth for every key.
- **English (`en`)** — secondary, parity-mirrored from `es`.

The metaproject intentionally keeps the landing bilingual rather
than multilingual. Each sibling app of the suite is responsible
for its own i18n — adding a third locale to the landing requires
both updating the landing AND ensuring the new locale is
supported in every sibling that ships its own picker. The default
locale is `es` because the suite's primary audience reads Spanish
first.

---

## 2. How detection works

### 2.1 On first visit

`js/bootstrap.js` runs **before** any other script (it's the
first `<script>` tag after the pre-paint inline). It:

1. Reads `navigator.languages` (an array of preferred locales,
   most-preferred first).
2. For each preference, lowercases and strips the region suffix
   (`es-MX` → `es`, `en-GB` → `en`).
3. Returns the first match against the `SUPPORTED` array.
4. Falls back to `'es'` if no preference matches.

### 2.2 On manual override

The language picker (`🇪🇸 / 🇬🇧` in the top-right of the
landing) overrides the detected locale for the rest of the
session. The override is **not persisted to `localStorage`** — the
landing is stateless on purpose; refresh re-detects from
`navigator.languages`.

### 2.3 On the `<html lang>` attribute

The active locale is mirrored into `<html lang>` for screen
readers and search engines. This is set on first paint (before
the stylesheets load) by the pre-paint script.

## 3. Where strings live

### 3.1 `js/strings.<locale>.js`

Every UI string lives in one of two files:

- `js/strings.es.js` — Spanish (default, source of truth).
- `js/strings.en.js` — English (parity-mirrored).

Each file exports a single `window.STRINGS` object with one
nested object per locale:

```js
// js/strings.es.js (canonical shape)
window.STRINGS = {
  es: {
    'meta.title': 'Apptonomia — suite de actividades',
    'meta.description': '…',
    'cards.calculia.name': 'Calculia',
    'cards.calculia.tagline': '…',
    // …
  }
};
```

`js/script.js` reads from `window.STRINGS[currentLocale]`. If a
key is missing in the active locale, it falls back to the `es`
block — this means **adding a key to `strings.es.js` is always
safe**; the landing will not break even before the `en` mirror
is added (it just shows Spanish until the mirror lands).

### 3.2 What is **not** in `strings.<locale>.js`

- **Technical code (HTML, CSS, JS, Markdown, JSON).** Always
  English. Variables, function names, identifiers, comments,
  commit messages — all English. This is the suite-wide language
  policy (see `CLAUDE.md` §B.2).
- **HTML `lang="es"` attribute on the meta documents** (the
  source Markdown / spec docs in `doc/<lang>/` — those are
  per-language files, not in `strings.<locale>.js`).
- **Project / repo names**: `calculia`, `memofun`, `okeymoney`,
  `routime`, `sinonimia`, `teclatlon` — always lowercase, no
  accents. The display name in each language is the
  human-readable form (Calculia, Memofun, etc.).
- **Pictograms / images**: ARASAAC pictograms keep their
  attribution in Spanish (the source language); each locale
  shows the same attribution.

## 4. Adding a third locale

The recipe below adds a new locale — for example, `gl` (Galician).

### 4.1 Checklist

1. **Create the strings file**: `js/strings.gl.js` with the same
   key set as `js/strings.es.js`, translated.
2. **Update the `SUPPORTED` list** in `js/bootstrap.js`:
   ```js
   const SUPPORTED = ['es', 'en', 'gl'];
   ```
3. **Add a button to the language picker** in `index.html`:
   ```html
   <button data-lang="gl" aria-label="Galego">🇬🇱</button>
   ```
4. **Update `scripts/check.js`** to include `'gl'` in the
   parity check:
   ```js
   var SUPPORTED = ['es', 'en', 'gl'];
   ```
5. **Update `README.md` + `README.es.md`** badges to list the
   new locale:
   ```
   [![i18n](https://img.shields.io/badge/i18n-es%20%7C%20en%20%7C%20gl-yellow.svg)](#-documentation)
   ```
6. **Translate the docs**: at minimum, add the language to the
   language picker's mirror in `README.md` / `README.es.md`. The
   full `doc/<lang>/` translation can come later (the landing
   ships before the docs do).
7. **Run `node scripts/check.js`** — must pass.

### 4.2 Things to verify

- Every key in `js/strings.es.js` has a translation in
  `js/strings.gl.js`.
- Every key in `js/strings.gl.js` also exists in `js/strings.es.js`
  (parity check is bidirectional).
- The language picker button has the right emoji / flag glyph
  for the new locale.
- The new locale's name appears in `<html lang>` when picked.
- The `?v=` content hash on the new `<script src="js/strings.gl.js">`
  tag is regenerated by `scripts/build-head.js`.

---

## 5. Things to **not** do

- **Don't** ship a locale where some keys fall through to the `es`
  fallback in production. CI (`scripts/check.js`) fails the build
  if any key in any locale's strings file is missing in any other
  locale's strings file.
- **Don't** use locale-specific CSS or HTML structures. The
  landing must render identically in every locale; the only
  differences are the strings.
- **Don't** introduce a per-locale file naming convention other
  than `strings.<locale>.js`. Each sibling of the suite uses the
  same `<locale>` token; consistency is what lets a future
  build-step share code across siblings.
- **Don't** store the active locale in `localStorage`. The
  landing is stateless on purpose; storing would add a third
  source of truth (alongside `navigator.languages` and the manual
  picker) without a corresponding gain.
